# QQ / SnowLuma / AstrBot 云端接入方案

状态：架构与适配计划，**还没有发布、实测完成的 AstrBot 专用插件或桌面远程记忆库模式**。不要把本文件当作现成的一键安装教程，也不要说只复制本地地址就已经接通云端。

## 放在哪里

```text
QQ ←→ SnowLuma ←→ AstrBot ←→ 聊天模型 API
                       │
                 爱之屋适配插件
                       │
            同服务器的爱之屋记忆服务
                       │
                  可选整理模型 API
```

SnowLuma 提供 QQ 与 OneBot 的协议连接；记忆的接入点选在知道实际会话与模型结果的 AstrBot 层。[SnowLuma 官方接入说明](https://snowluma.github.io/en/docs/guide/connect-bot)

推荐让无界面记忆服务跟机器人运行在同一台阿里云服务器，通过回环地址通信。这样个人电脑关机后，云端机器人仍可存取记忆。需要补齐服务进程部署、持久数据卷、重启恢复与云端凭据保管，再作为受支持的服务端交付。

当前 macOS App 启动自己的本机服务，没有远程库选择器，也没有跨设备同步。服务器记忆不能靠桌面自动读取云端硬盘；受保护的远程管理入口需另行适配。现有控制器只监听回环地址，不能直接改成公网监听就宣称安全部署完成。

## AstrBot 插件应做的事

官方提供模型请求前、Agent 完成、回复装饰和消息发送后的事件钩子。接入时按实际版本核对，区分中间工具调用、最终生成结果和实际送达结果，不能把一轮拆成多个重复完整对话，也不能把失败发送冒充已送达。[AstrBot 官方事件文档](https://docs.astrbot.app/dev/star/guides/listen-message-event.html)

1. 按用户明确选择的 QQ 私聊／群聊过滤，未绑定的消息在入队和落盘之前忽略。
2. 模型回复前，通过固定连接的 context 接口检索本库资料，保留角色和证据标记。
3. 实际收到的用户消息、最终回复、工具结果分开记录状态。使用平台消息 ID、宿主运行 ID 和稳定会话 ID 去重；中断、超时和重试保留真实状态。
4. 爱之屋暂时不可用时，把指定会话事件放在插件自己的私有持久队列，重连后补交；不能因此抓取其他聊天或扩大范围。
5. 记忆整理继续由爱之屋按用户配置、版本化规则与预算执行，QQ 插件只负责真实记录与回忆交换。

## 会话与存档隔离

AstrBot 的 UMO 表示具体平台实例下的消息来源，可用 `/sid` 核对来源。不能只按昵称或模型名绑定。[AstrBot 官方会话说明](https://docs.astrbot.app/use/command.html)

建议映射包含平台实例、机器人身份、消息类型、UMO，以及群聊需要时的发送者范围。不同私聊默认独立；群聊是共享库还是按成员分库，必须明确选择。一个连接令牌只能访问其固定存档，不能让模型自行枚举或切换其他存档。

用户要延续同一 Agent，可明确把新 QQ 会话绑定原库；要独立人格则新建空库。跨私聊和群聊共享记忆不是默认功能。

## 用户侧的目标配置流程

未来插件应让用户只填写：爱之屋服务地址、爱之屋生成的绑定令牌／绑定码、目标 QQ 来源，以及目标存档。提供“测试连接”“测试记录”“测试回忆”“暂停”“断开”并分别显示结果。

绑定令牌是爱之屋的库访问凭证，不是模型厂商 API Key。聊天模型继续用 AstrBot 自己已有配置；用户想让爱之屋调用大模型整理时，才为整理器配置可选模型。不能要求仅为记忆连接重复提供聊天模型密钥。

这条路线可以复用本项目的固定连接、events/context、幂等、原始档案和使用反馈协议，但仍需独立插件实现与真实 AstrBot / QQ 流程验收。本次 macOS 0.7.0 没有声称已经交付这些云端功能。
