# 爱之屋 AstrBot 经历记忆适配（实验版 0.1.0）

这不是另一个 QQ 机器人，也不替换 SnowLuma、AstrBot 的聊天模型或人格。它把管理员明确登记的同一 Agent 的多个消息来源汇入爱之屋，再把少量相关记忆提供给本轮模型请求。可见对话和实际观察是经历证据，工具参数、工具调用列表和私有推理不是主要记忆。

**状态：实验版。2026-10-30 已在 macOS、AstrBot 4.29.3、DeepSeek 与 QQ 官方接口 / WebChat 完成首轮真实接入、跨平台回忆、隔离和断线补交验证；SnowLuma / OneBot、云服务器、其他版本及长期运行仍未验收。** 不宣称可以自动观察这条鱼在任何软件里的全部行为。

## 接口基线

依据 2026-10-30 的 AstrBot 官方文档与源码编写，使用现代 `on_llm_request`、`on_agent_done`、`on_llm_tool_respond`、`after_message_sent` 钩子，以及 `TextPart.mark_as_temp()`。最低接口目标为 AstrBot 4.24.0；这是接口要求，不代表所有版本均已实机验证。

- [官方事件钩子文档](https://docs.astrbot.app/dev/star/guides/listen-message-event.html)
- [官方 ProviderRequest / LLMResponse 源码](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/provider/entities.py)
- [官方 Agent 钩子分发源码](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/astr_agent_hooks.py)
- [官方插件配置文档](https://docs.astrbot.app/dev/star/guides/plugin-config.html)

## 安装与绑定

1. 在 AstrBot 所在服务器运行支持“Agent 活动来源”的爱之屋服务。桌面版程序不能直接当成 Linux 安装包；云端进程管理、凭据保管和远程管理需要使用项目明确支持的部署方式。
2. 在爱之屋选择这条鱼的已有存档，登记一个 `adapter=astrbot` 的活动来源，允许平台例如 `qq`，填写由管理员确认的宿主 Agent 标识。保存它生成的私有来源配置文件。**这不是模型厂商 API Key，不需要重复填写聊天模型密钥。**
3. 将本目录的完整内容复制到 AstrBot 的 `data/plugins/astrbot_plugin_love_house/`，保留 `LICENSE`、`bridge.py` 与随包 SDK。也可用 `package.py` 生成独立 ZIP 后按所用 AstrBot 版本支持的 ZIP 安装方式导入。
4. 打开 AstrBot 插件配置，增加一项“Agent 活动来源绑定”：填写同一个 `runtime_agent_id`、这台服务器上的私有配置完整路径，以及属于这条鱼的若干 UMO。用 AstrBot `/sid` 核对消息来源。配置路径不会被当作网络地址，也不会读取其他文件夹。
5. 同一条鱼的多个私聊/群聊放在同一项绑定中；另一个 Agent 新建另一项、指向另一份来源配置。一个 UMO 同时出现在两项中会拒绝加载，避免归属不清。
6. 保存并重载插件，再启用。“启用”默认关闭；空名单不采集。聊天模型与 QQ 连接沿用 AstrBot 自身原有配置。

本项目是包含多个组件的仓库，仓库根目录不是可直接安装的 AstrBot 插件目录。当前不提供插件市场或仓库根目录自动更新承诺；独立 ZIP / 完整目录是本实验版的交付方式。

### 关于稳定 Agent 身份

私有配置中的来源身份、Agent 标识和平台会相互校验，每次回调也会检查配置没有被换成另一条鱼。该插件采用管理员明确配置的 UMO 路由，不用昵称、模型名字或模型自述推测身份。

目前没有声称读取到 AstrBot 各执行器通用的自动 Agent UUID。如果一个 UMO 改成另一人格或另一个 Agent 运行，应先停用、确认归属后修改绑定；不能只改模型昵称就认为身份已经重新识别。以后宿主提供稳定身份路由时，可继续使用同一份爱之屋存档。

## 实际记录与回忆

- 模型请求前保存实际平台用户原话的待完成记录，查询本轮相关资料。资料追加为临时用户内容块，不改原人格或 system prompt，不持久写回宿主聊天历史。
- 同一事件的多个工具步骤复用一次取回结果；给后续请求继续提供同一份有界资料，不按循环次数反复查询。
- 只在最终助手生成结果时配对完整对话，过滤流式片段、工具调用中间步骤和错误响应。状态是 **generated**，不等同 QQ 送达或已读。
- 发送后回调只记录“宿主完成发送阶段”的观察。它没有收件人送达、阅读证明，不会标记“对方已看到”。
- 工具结果只提取宿主实际提供的文字内容作为观察，不保存参数、工具名、原始 provider completion、私有推理或媒体文件。没有错误标记时仍只是 `observed`，不能据此推断网页操作已经成功；有明确 `isError` 时保留 `failed`。
- Agent 接触的 QQ 发言者可能是第三方，插件附带发送者标识及 `platform_sender` 来源标签；不能直接把所有发言者的偏好当成主人的偏好。服务端整理必须继续核对参与者与证据。
- 为什么这样做、发生了什么、结果如何，由爱之屋基于原话和观察整理成经历。没有证据的原因和结果保留未知，不编故事。

## 队列、恢复与覆盖范围

回调先写私有 SQLite，再由后台 worker 交给随包 SourceClient；QQ 的发送流程不会等待存档网络请求。取回资料最多等待约 1.2 秒，失败后聊天继续。

插件的 `ready` 原文在 SDK 确认已持久排队或服务端已经确认归档后才清除。重复最终回调通过稳定平台消息编号去重；同编号不同正文不会覆盖旧内容。未完成或没有最终文字的用户消息保留为 `awaiting_final`，不会伪装成完整经历。

SDK 的单次数据与待交队列有操作预算，队列满时插件保留 `ready`，恢复服务后继续补交，不按日期清理原文。磁盘写入失败或单条超过 40,000 字时，会明确告警，不能把未存资料说成已采集。这里的操作预算不是记忆保存期限。

管理员可在目标会话发送 `/lovehouse_status` 查看配置状态和等待数量，不回显原文、UMO、配置路径或令牌。**已配置不代表已经验证全部活动覆盖**，要用下面的一轮验收确认真实落盘。

本插件没有观察到的活动不会自动出现：独立浏览器 Agent、绕开上述钩子的定时任务、其他软件中的活动，需要在对应执行器接入同一 Agent 来源。没有文字输出的图片/语音/工具块不会被假装看懂；收件人已读和隐藏模型推理不在覆盖范围。

如果用户要求真正忘记某段资料，服务端会按其规则清理存档，但不应声称能自动远程清掉所有外部客户端副本。停用来源后，还应处理本插件未完成日志和 SDK 待交队列。完成记录在插件日志中只留去重哈希，不长期重复保存已交出的对话正文。

## 一轮实机验收

使用临时鱼和合成记录，不用真实私聊或厂商密钥做测试：

1. 在登记的 UMO-A 发一句测试约定，收到最终回复后确认爱之屋该存档有原话与助手回复，记录状态为生成而非已读。
2. 在登记的 UMO-B 询问同一约定，确认取回来自同一鱼；在未登记的 UMO-C 发不同测试内容，确认没有进入插件队列或爱之屋。
3. 让宿主执行一次能返回文字的测试工具，检查实际观察与完整回复分开，不产生多份完整轮次，也不把失败当成功。
4. 暂停爱之屋服务，完成一轮测试聊天，确认待交数量增加且 QQ 仍能回复；重开服务和插件后确认补交一次，没有重复。
5. 使用不同来源配置建立另一条鱼，确认它查询不到前一条鱼的测试约定。

只有以上在所用版本中跑通后，才能把该环境标记为“实机验证”。

## 源码维护与打包

`source_client.py` 是项目 SDK 的受控副本，不依赖整个 `nkb` 包。修改 SDK 后，在完整项目中执行：

```sh
python3.12 extensions/astrbot-love-house/package.py --sync-client --check
python3.12 -m unittest tests.test_astrbot_adapter -v
python3.12 extensions/astrbot-love-house/package.py --output dist/LoveHouse-AstrBot-0.1.0-experimental.zip
```

打包只允许固定源码清单，不包含配置、消息数据库、队列或 `__pycache__`。自有代码使用 PolyForm Noncommercial 1.0.0，保留作者 myflww 署名。
