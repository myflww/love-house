# 爱之屋 macOS 0.9.0 验证说明

版本0.9.0，macOS构建号12，服务协议继续0.4.0。当前轮次先交付本机版本，公开上传和其他系统同步按用户后续安排，不覆盖既有Windows修复或移动端工程。

## 本职能力

1. **输出接收**：已登记运行程序可提交完整对话、真实文字观察或独立助手输出。独立输出保留assistant归属，不捏造user，不自动认定内容所说的世界事实。接收采用固定库身份、稳定事件与私有队列。
2. **自动取回**：已整理／用户确认记忆有独立检索通道，再加入有界原始资料；明确平台近期更正仍优先。资料包和来源界面统计实际返回的整理、原始及其他材料，不声称模型一定采纳。
3. **清楚配置**：界面按Harness、AstrBot、其他MCP程序提供接收方、填写位置、验证标准。本机路径、云服务器和整理Key的用途分别说明，帮助可展开与收起。

AstrBot适配器0.2.0在`on_agent_begin`补入记忆，覆盖默认流程绕过普通请求前hook的情形；主动任务开关默认关闭，仍要求原UMO白名单及实际平台类型校验。Harness适配器0.4.1只为已固定或已由真人绑定的根会话增加无人输入输出和回忆，不用独立工作自抢新窗口。

AstrBot发送后的投递阶段仅留在插件私有元信息中，不再生成可回忆节点；状态命令也不会被包装为助手经历。独立助手输出的图谱正文和整理器引用统一使用已验证的`text`字段，不接受旧工具`content`别名覆盖。

外部平台参与者提出“导入人格”时，其话语继续保存；人格设置由存档管理者在本机确认，不将来源消息当作管理权限。

## 真实整理记忆因果验收

本次复用了原实验库里已经实际出现过的一条QQ助手输出，明确标为历史输出重放，在私有临时库运行0.9代码。没有新发QQ消息，没有把测试记忆写入生产存档，也没有用手工正确答案替换模型产物。

- 实际整理模型调用一次，经过现行逐字、角色和来源检查，创建1条整理记忆，候选0条。
- 通过同鱼另一来源、新会话的正常SDK `read_context`，实际取回该整理节点。
- 保留原文用于安全核验，仅将这次真实检索到的整理记录投影给全新接收会话：独立原始记录0条，历史消息0条。整理记录自身的正式引用保留。
- 接收模型回答正确的新口令与被替换的旧口令。
- 相同问题与配置的空记忆对照表示无记忆，没有给出答案。
- 只使用经用户许可的3次供应商请求，不自动重试；每次先记入原库调用账本，结束恢复原整理开关与每日上限6。临时样本退出清除，长期日志只保留计数、布尔结果与固定错误码，不含原话、答案或Key。

此验证通过的是**已整理的历史助手陈述可被下一次模型实际使用**，不是证明所有主张都真实，也不是把0.8的“真实生活经历自动归纳未通过”改写成全部通过。

## 性能观察

在本机合成数据中，各做5次查询：1000条原始记录和20条整理记录的锁内路径中位数约99ms；5000条原始记录和20条整理记录约473ms，同规模旧回环／副本路径约552ms。两个规模都实际返回8条整理记录及原始兜底。它是当前机器的少量样本，不是任意规模和硬件的时延承诺；大库仍使用JSON存储，后续需持续测量。

## 接入与验证边界

QQ官方接口／WebChat的首轮实机结果沿用0.8记录；新增Cron和Harness无人输入路径有固定版本官方消息转换与真实接口契约离线测试，尚未把它们标为各平台全部实机通过。SnowLuma、NapCat、微信、云端、其他runner和纯多媒体输出需各自验证。未接入的独立执行器不会被自动观察，无法识别的事件不会被包装成完成。

本轮未静默扩大既有生产连接范围，未读取AstrBot模型Key，没有上传私有实验目录。
