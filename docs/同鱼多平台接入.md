# 同一条鱼在多个平台的记忆

爱之屋用一份记忆库保存一个 Agent 的经历。QQ 交流、网页观察、定时任务等资料，可以由多个已接入的宿主汇入这份库，再整理成“什么时候、做了什么、为什么、结果怎样”的经历。

接入时不需要重新提供这条鱼的聊天模型 API Key。只有希望爱之屋调用模型协助整理时，才需要为“记忆整理”单独配置模型凭据。

当前 AstrBot 插件是**实验版**：已有源码、独立插件包和本地契约测试，尚未完成真实 QQ、SnowLuma、AstrBot 或阿里云环境的实机验收。SDK 和无界面服务已用临时进程与合成资料验证；这也不等于某个真实养鱼环境已经接通。

## 先确定一条鱼的身份

| 配置项 | 用途 | 同一条鱼增加平台时 |
| --- | --- | --- |
| 记忆库 `library_id` | 爱之屋固定的存档身份，决定资料存到哪里、能从哪里取回 | 继续选择同一份库 |
| 宿主 Agent 标识 `runtime_agent_id` | 宿主适配器明确登记的稳定身份 | 在各宿主中保持明确、稳定的对应关系；本文示例统一为 `fish-luma-001` |
| 活动来源 `source_id` | 一个采集宿主的独立凭证与接收状态 | 不同执行器分别生成，方便单独暂停或断开 |
| 会话或平台标识 | 说明这段经历来自哪里 | 可以有多个，例如 QQ 的几个 UMO、SDK 的 `browser` 平台 |

给鱼换模型、API Key、昵称或聊天窗口时，可以继续使用原库。另一条鱼应新建另一份库，并为它生成独立来源。相同昵称不会使两份库合并。

`runtime_agent_id` 由宿主配置和实际消息路由共同保证；爱之屋会核对报送值与登记值。它不是远程身份认证，也不能靠模型说“我是某某”来证明。管理员应只把一个来源的私有配置交给它实际负责的宿主。

## macOS：从“同鱼活动来源”接入

1. 打开爱之屋，点击左上角的记忆库名称，选中这条鱼已经使用的库。新鱼可以点“＋ 新记忆库”。
2. 在记忆库面板点击“同鱼活动来源”。弹窗标题为“同一条鱼 · 活动来源”，顶部会显示当前存档。
3. 展开“添加一个活动来源”，填写来源名称，选择“AstrBot · 实验适配”或“其他执行器 · SDK”，填写宿主里的固定 Agent 标识。
4. 核对归属后，勾选“我确认这个宿主属于当前这条鱼，配置只交给该宿主”，点击“生成来源配置”。
5. 点击“复制配置路径”，把这个本机私有文件路径填入对应宿主。生成路径只完成了登记；宿主加载并上报一轮真实资料后，才会出现“已收到真实记录”。

这个私有文件包含来源访问凭证。界面只展示文件路径；不要把文件内容放进公开仓库、截图或分享存档。Mac 上生成的路径只适用于这台 Mac，不能原样填到云服务器。

同一条鱼另有一个独立浏览器执行器时，在**同一份库**再添加一个 SDK 来源，并在浏览器执行器里接入。若这些平台都由同一个 AstrBot 宿主负责，可以让同一个来源接收管理员已登记的多个消息路由，不必为每个 QQ 窗口重复建库。

来源卡片支持“配置路径”“暂停 / 继续”“断开”。暂停或撤销某个来源只改变该来源，已有记忆保留，其他来源继续工作。已断开的来源要重新接入时，生成新的来源配置。

原有的“连接 Harness 窗口”仍使用原来的窗口范围。它不会因为新增“同鱼活动来源”就自动扩展到 Harness 的所有会话。

## AstrBot：明确登记哪些消息属于这条鱼

在来源管理中点击“导出 AstrBot 实验插件”，可保存独立 ZIP；包内只有插件源码和使用说明，不包含个人记忆或连接凭证。按所用 AstrBot 版本支持的 ZIP 安装方式导入，也可以将完整插件目录放到 `data/plugins/astrbot_plugin_love_house/`。项目仓库根目录不能直接当作 AstrBot 插件目录。

在 AstrBot 插件配置中，添加一项“Agent 活动来源绑定”：

```json
{
  "enabled": true,
  "record_observations": true,
  "bindings": [
    {
      "runtime_agent_id": "fish-luma-001",
      "source_config_path": "/这台服务器上的实际路径/source_实际来源标识.json",
      "allowed_umos": ["替换为通过 /sid 核对的 UMO-A", "替换为实际 UMO-B"],
      "platform": "qq"
    }
  ]
}
```

这段示例用于说明字段；路径与两个 UMO 都必须替换，不能直接复制示例值启用。插件默认 `enabled=false`，空消息名单不采集。

- 在 AstrBot 用 `/sid` 核对实际 UMO，把确认属于同一条鱼的多个私聊或群聊填在同一项绑定里。
- `runtime_agent_id` 必须与该私有来源文件一致。`platform` 也必须属于来源允许的平台范围。
- 一个 UMO 同时出现在两项绑定中会拒绝加载，避免把同一段资料交给两条鱼。
- 某个 UMO 如果改由另一人格或 Agent 使用，应先停用并重新核对归属，再修改绑定。

插件只处理已登记 UMO，模型请求前取回有界的相关资料，最终生成回复后记录完整轮次。生成结果记为 `generated`；宿主完成发送阶段也不能证明收件人已收到或已读。平台发言者可能是第三方，不会仅因出现在 QQ 里就被认作鱼的主人。

QQ 之外，独立浏览器 Agent 或其他执行器如果没有经过这个插件的钩子，需要另外接入 SDK。可以在已登记的目标会话发送 `/lovehouse_status` 查看插件状态和等待数量。完整接口要求、安装步骤和验收清单见 [AstrBot 实验插件说明](../extensions/astrbot-love-house/README.md)。

## Linux 云服务器：爱之屋服务与 Agent 在同一台机器

适用于 AstrBot、SnowLuma 相关宿主或其他 Agent 已运行在云服务器上的情况。这里运行的是**源码中的无界面记忆服务**，不需要安装 macOS 桌面程序。需要 Python 3.11 或以上，以及完整项目源码。

以下示例在 Linux 的 Bash 中执行。目录可自行选择，但重启后必须继续使用原来的 `--data-dir`。

```bash
git clone https://github.com/myflww/love-house.git
cd love-house
python3 -m venv .venv
.venv/bin/python -m pip install -e .

.venv/bin/python scripts/run_memory_service.py \
  --data-dir "$HOME/.local/share/love-house"
```

命令保持运行后，在**同一台服务器的另一个终端**进入同一个项目目录，登记 AstrBot 来源：

```bash
.venv/bin/python scripts/configure_agent_source.py \
  --data-dir "$HOME/.local/share/love-house" \
  --library default \
  --name "同一条鱼的 AstrBot 宿主" \
  --adapter astrbot \
  --runtime-agent-id fish-luma-001 \
  --platform qq
```

命令输出来源元数据和 `private_path`，不打印连接令牌。把实际的 `private_path` 填入**这台服务器**的 AstrBot 插件，再按上一节登记 UMO。配置文件默认以私有权限保存，运行插件的系统用户还需要有权读取它并写入其私有队列目录。

如果还有一个独立网页执行器，给同一库添加另一来源：

```bash
.venv/bin/python scripts/configure_agent_source.py \
  --data-dir "$HOME/.local/share/love-house" \
  --library default \
  --name "同一条鱼的网页执行器" \
  --adapter sdk \
  --runtime-agent-id fish-luma-001 \
  --platform browser
```

`--platform` 可以重复填写，以限定同一个来源允许报送的平台。不填写时，当前命令登记为 `*`，只表示允许该来源声明的平台，不表示爱之屋已经适配或监听了所有软件。

`default` 是全新服务自动创建的空白库身份。使用其他已有库时，应把 `--library` 换成该库的固定 ID，而非界面显示名称；命令不会自动创建它，也不会从 Mac 同步记忆。新增来源时要执行登记命令，普通重启则继续使用已有私有配置，不要每次再建一个来源。

服务默认没有示例库、不配置模型、不调用整理模型，控制器只监听本机 loopback。命令不会安装系统服务；需要长期运行时，由部署者选择自己的进程管理器启动同一命令并负责重启。不要用两个进程同时打开同一个数据目录。

### SDK 宿主实际要做什么

SDK 不会自行读取窗口。执行器需要在知道“当前动作属于哪条鱼”的位置加载对应的私有配置，并在真实事件发生后报送。最小调用形式如下：

```python
from nkb.service.source_client import SourceClient

memory = SourceClient("/这台服务器上的实际来源配置文件.json")

# 在一轮请求开始时读取相关资料，供宿主按证据使用。
material = memory.read_context("本轮实际话题", "实际会话编号", max_chars=8000)

# 在真实完成的一轮对话结束后报送，event_id 使用宿主稳定事件编号。
memory.record_dialogue(
    "实际用户原话", "实际生成的最终回复", "实际会话编号", "稳定的对话事件编号",
    platform="browser", delivery_status="generated",
)

# 网页执行器确实观察到了什么，就记录什么；原因和成功结果不能猜。
memory.record_observation(
    "宿主实际观察到的页面结果", "实际任务编号", "稳定的观察事件编号",
    platform="browser", outcome="observed",
)
```

这些是接入代码示例，不是向爱之屋发送测试文字的指令。实际集成要由对应宿主在生命周期钩子中调用，并提供真实文本与稳定事件编号。可用 `occurred_at` 传入宿主掌握的实际发生时间，单位为 Unix 时间戳秒；离线补交时继续保留它。调用失败时 SDK 的私有待交队列可恢复补交，宿主仍应检查状态，不把未保存的资料说成已存档。

不必为了记忆编写一长串工具调用明细。对经历有意义的观察、参与者原话、发生时间和实际结果，才是整理依据。相同事件重试应复用相同 `event_id`；不同正文不能借用同一个事件编号覆盖旧记录。

## 云端启用模型整理：显式注入一份整理密钥

“接入并存下原文”与“调用模型整理经历”可以分别配置。需要模型整理时，可以为爱之屋提供独立凭据；已有宿主的聊天模型连接不受影响。

先停止前台运行的记忆服务，再按下面方式启动同一数据目录。示例通过 Bash 隐藏输入读取密钥，命令行参数只填写环境变量的**名字**。将地址和模型 ID 替换为自己服务商实际支持的值。

```bash
read -r -s -p "请输入爱之屋整理模型密钥：" LOVEHOUSE_ORGANIZER_KEY
printf '\n'
export LOVEHOUSE_ORGANIZER_KEY

.venv/bin/python scripts/run_memory_service.py \
  --data-dir "$HOME/.local/share/love-house" \
  --organizer-key-env-name LOVEHOUSE_ORGANIZER_KEY \
  --organizer-base-url https://your-model-provider.example/v1 \
  --organizer-model your-organizer-model \
  --organizer-library default \
  --organizer-trigger-count 20 \
  --enable-organizer
```

这组参数的含义：

| 参数 | 行为 |
| --- | --- |
| `--organizer-key-env-name` | 只读取明确指定的那一个进程环境变量，不尝试其他应用或常见厂商变量名 |
| `--organizer-base-url`、`--organizer-model` | 本库整理所用的地址和模型；远程地址须 HTTPS，本机 loopback 调试允许 HTTP |
| `--organizer-library` | 要整理的已有库，默认 `default` |
| `--organizer-trigger-count` | 批次触发阈值，默认 20，允许 1—500；这是工作调度阈值，不是记忆容量或保留期限 |
| `--enable-organizer` | 明确允许启动后进行模型工作；去掉它仍可加载临时凭据，但整理保持关闭 |

密钥只进入当前进程的会话凭据，不写入爱之屋的 JSON 配置、日志或启动参数。地址、模型和阈值等非密钥设置会随库保留。下一次启动服务时，进程管理器必须重新向该进程注入指定变量，再使用相同参数；本软件不会替管理器持久保存密钥。只有一段 shell 输入而没有配置管理器环境时，不能承诺机器重启后自动恢复这份密钥。

自动整理按阈值和内部批次预算处理待整理资料，不保证每满 20 条就恰好只产生一次模型请求。保留原始证据，整理出什么、原因与结果是否有依据，仍受爱之屋底层规则校验。缺少依据的部分保持未知。

## 重启、同机地址与多设备

在同一台机器上，重开爱之屋服务并继续使用原数据目录后，已登记的来源和记忆保留。SDK / 插件保留原私有配置并继续运行时，会按其重试机制补交；不需要重新登记每个平台。聊天宿主、插件和服务本身仍需由各自的启动方式启动，不能把“配置文件已生成”当作这些进程都已开机自启。

`127.0.0.1` 和 `localhost` 指向**运行当前程序的那台机器**。Mac 上的 localhost 不会指向阿里云；云服务器的本地路径也不会成为 Mac 文件路径。AstrBot 若在容器里，容器内的 localhost 属于该容器，部署者要先解决受支持的同机通信与私有路径挂载，不能直接照抄宿主机路径就声称连接完成。

本文的云端方案要求服务与采集宿主能在同机边界内访问本机地址和私有文件。当前没有提供“一键从 Mac 桌面远程管理云端来源”或“自动建立公网 HTTPS 服务”的部署承诺；不要为套用示例而直接公开本机管理接口。需要跨机器部署时，应另行设计明确的认证、HTTPS、私有配置和数据迁移方案，并实机验证。

## 用一轮小测试确认真正接通

建议先建一条临时测试鱼，用合成内容完成以下检查：

1. 在登记的 QQ 来源说一句测试约定，确认原话与最终回复进入目标库；同时检查来源卡片或插件状态。
2. 在同鱼的另一个已接入来源询问这个约定，确认读取到同库材料。另鱼的来源应读不到它。
3. 在未登记 UMO 或未接入执行器中说另一句测试内容，确认不会被采集。
4. 让执行器返回一次真实可见的测试观察。启用整理后，在“她的经历”中核对发生时间、事情、原因和结果，并检查其依据；记录条数不应被误读为经历件数。
5. 暂停服务完成一轮测试，再恢复服务与插件，检查等待资料补交且不重复。再单独暂停一个来源，确认其他来源仍能工作。

只有这轮检查在实际部署版本上通过后，才能确认该来源覆盖了相应活动。复制配置、添加平台名字或开启一个后台窗口，都不会让爱之屋自动观察未接入软件中的行为。
