# QQ / SnowLuma / AstrBot 接入

0.8.0 已提供 AstrBot **实验插件**、同鱼来源登记和无界面记忆服务。实际操作以 [同鱼多平台接入](同鱼多平台接入.md) 与 [插件 README](../extensions/astrbot-love-house/README.md) 为准。实验插件的本地契约测试不等于真实 QQ、微信或阿里云验收。

```text
QQ / 其他已适配平台 ←→ 协议桥 ←→ AstrBot ←→ 聊天模型
                                    │
                           爱之屋活动来源插件
                                    │
                          同服务器的记忆服务
                                    │
                         可选的记忆整理模型
```

接入点在知道真实消息和最终结果的宿主。SnowLuma 负责它所支持的协议桥，爱之屋不替代它，也不需要重复取得聊天模型 Key。[SnowLuma 官方接入说明](https://snowluma.github.io/en/docs/guide/connect-bot)

一条鱼对应同一份记忆库，管理员可为它登记多个 UMO 或独立执行器。UMO 是来源和情节标识，不能按每个 QQ 窗口机械拆成新鱼；也不能把一个机器人账号的所有人物混在一起。当前实验插件依据管理员明确配置的 UMO 路由和真实平台元信息核对归属，未登记活动在读取正文前忽略。

插件在模型请求前读取本库相关记忆，最终生成后提交完整对话，工具钩子仅提交可见观察；没有默认收集每次工具参数、私有推理或整机其他窗口。结果记为生成、观察或来源报告；发送后阶段不证明 QQ 已送达或已读。[AstrBot 官方事件文档](https://docs.astrbot.app/dev/star/guides/listen-message-event.html)

记忆以真实事情为中心，整理成时间、经过、明确表达的缘由与结果。原始资料只作为可核对依据；缺少原因时保持未知，不由模型猜测。独立浏览器执行器需要额外来源接入同一库，不能靠昵称或模型自称来合并身份。

云端可以把记忆服务与 AstrBot 放在同一台 Linux 主机，在回环地址交换资料；容器则需明确处理私有配置文件权限和网络命名空间。重启后继续使用同一数据目录，整理 Key 由用户指定的进程环境重新注入。项目目前不代装 systemd、不开公网端口、不实现 Mac 桌面远程库管理或跨设备同步。

首次实机至少检查：A 会话记录、同鱼 B 会话回忆、未登记 C 不采集、另一鱼无法取得 A 的资料、停服务后恢复补交。真实平台及账号验收应单独记录，不以“复制配置成功”代替。
